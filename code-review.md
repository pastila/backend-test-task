
# Общее
## Архитектура
По директориям Domain, Infrastructure кажется, что должен был быть DDD. Однако не произошло разделение по слоям.  Часть доменной логики утекла в контроллеры или другие сервисы. Отсутствует слой Application. 
# По файлам
## Controller
### AddToCartController
Метод для добавления товара в корзину называется `get`. Нужно переименовать. Название должно отображать действие. Если хочется использовать одно наименование для всех контроллеров, то лучше тогда использовать handle или invoke.

Получение данных в сыром виде и передача дальше без валидации. Нужно использовать DTO с необходимой структурой и типизацией.

Создание CartItem с генерацией UUID не должна происходить в контроллере. Это операция должна происходить внутри корня агрегата. Cart->addItem($productUuid, $quantity)

Не вижу сохранение корзины

В целом весь код лучше вынести из контроллера и поместить в отдельный хэндлер/сервис.

### GetCartController
Странный if. К последнему return код никогда не придет.

### GetProductsController
`$this->productsVew->toArray($rawRequest['category'])` - передаются сырые данные. `productsView` ожидается что будет каким-то декоратором или нормалайзером, а в него передается строка.

Получается, что контроллер должен выдавать список товаров по категории. По названию контроллера вообще этого не понять. При этом контроллер ждет данных из body, хотя для этого экшена ожидается использование GET.

### JsonResponse
Предполагаем, что тут есть реализация? При использовании этого Response постоянно прописывают Content-Type, хотя название класса предполагает что эти заголовки будут уже указаны. 

## Domain
### Cart
Uuid по хорошему сделать бы VO, как и PaymentMethod, чтобы сущность сохраняла инвариантность.

`addItem` изменить на `addProduct` - агрегат сам должен отвечать за создание, а не внешняя система.

Добавить поле totalPrice. Ответственность за рассчет общей стоимость так же надо сохранять внутри домена.

Customer и paymentMethod могут приходить только в момент создания заказа - они не должны быть в конструкторе.

### CartItem
Тоже самое про VO для сохранения инвариантности. 

### Customer
Тоже самое про VO для сохранения инвариантности. Возможно вообще лучше из entity переделать в VO. Но тут уже вопрос к бизнес логике.

## Infrastructure
### Connector
Нужно добавить ConnectorInterface с четкими сигнатурами методов. По-хорошему напрямую к инфраструктурным реализациям напрямую не стоит обращаться.
Название класса не описывает его содержание. 

`public function get(Cart $key)` - непонятная сигнатура. `Cart` должно быть возвращаемым значением. 

Лучше не хранить данные в serialize. Слишком много проблем может возникнуть. Лучше все же в json.

### ConnectorException
Не надо заново изобретать Exception

### ConnectorFacade
Это не фасад, а Factory или Builder. Вообще не похоже, чтобы в таком виде этот класс должен существовать. Нужен какой-нибудь registry для хранения подключения.

Тип для $connector не указан. Остальные поля все публичные - так не надо делать

## Repository
### Product
Непонятно как очутился в директории Repository. readonly модель лучше переименовать в что-нибудь типа ProductView и перенести в ACL.

### CartManager
Не надо наследовать `ConnectorFacade`. Источник данных должен подключаться через DI по интерфейсу.

Ошибка сохранения тихо умирает. Это серверная ошибка и должна дойти до клиента. Иначе поведение остается непредстказуемым.

Logger инжектится через setter, но нет проверок при его вызове - возможна ошибка.

Опять же нет возвращаемых значений методов. phpdoc прописаны некорректно.

### ProductRepository

Принимаются сырые данные и передаются в запрос - категорические нельзя так делать. Нужно использовать PDO. Раз используется Doctrine\DBAL\Connection, то видимо можно и с Repository doctrine работать?
В запросе используется `SELECT *` - не очень хорошая практика. Надо именовать все запрашиваемые колонки.

Судя по всему есть поле `is_active` при запросе по категории используется, а при запросе по uuid спокойно получает и добавляет в корзину - ошибка.

В `getByCategory` запрашивается только id, но гидрация происходит всех полей - ошибка.

В make длинный список аргументов - может сломать в любой момент при смене сигнатуры. Рекомендуется использовать именованные аргументы. Так же проверки на сущестовавание ключа, нет приведения типов

## View
### CartView
Переименовать в `CartNormalizer`. `CartView` ожидается как DTO (хотя даже так лучше было бы `CartOutput` например).

### ProductView
Класс пытается и получить данные по строке категорий и потом привести их к нужному виду. При этом называется `ProductView`.  Нужно так же переименовать в normalizer, убрать получение данных изнутри. Оставить только нормализацию.
